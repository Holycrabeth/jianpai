# 中文交互规范

当前第一阶段只汉化 Pi 原有显示：`read → 读取`、`write → 撰写`、`edit → 修改`、`bash → 执行命令`。下文的目的、影响和下一步结构是后续改善时的参考，不要求第一阶段新增解释卡片。

## 基本原则

- 面向成年人，用清楚的中文，不居高临下，不把用户称为“小白”。
- 先说用户关心的事，再补技术细节。
- 术语首次出现时用一句话解释，避免堆砌英文缩写。
- 路径、命令、代码、错误码保持原样，不做破坏性的翻译。
- 解释和原始输出分开标注；解释不是原始日志的替代品。
- 不展示或编造模型的内部思考，仅说明操作目的与可观察的结果。

## 工具信息结构

按需要展示，而不是每次强制输出所有字段：

1. **操作**：正在做什么，例如“查看项目配置”。
2. **对象**：哪个文件、目录或命令。
3. **目的**：仅在上下文支持时说明；不知道就不猜。
4. **影响**：是否修改文件、访问网络，无法判断时明确说明。
5. **结果**：完成、失败、取消，或仍未验证。
6. **下一步**：用户是否需要处理。
7. **技术详情**：保留原始数据，以便排错。

## 推荐表达

| 避免 | 推荐 |
| --- | --- |
| 执行 bash | 执行终端命令，并保留命令原文 |
| 写入成功，项目好了 | 文件已写入，尚未检查能否运行 |
| 报错了 | 检查未通过；下方保留具体错误信息 |
| 肯定是网络问题 | 请求失败；目前还不能确定是否由网络引起 |
| 这是安全命令 | 说明已知影响，不对未知脚本作安全承诺 |

## 示例：修改文件

```text
正在修改页面标题
文件：src/app.ts
影响：将修改这个文件的部分内容

文件已修改
尚未启动页面验证显示效果
```

只有实际知道修改目的是页面标题时才使用上述标题；否则使用“正在修改文件”。

## 错误与长日志

- 默认展示简短结果，不将整屏技术日志作为唯一反馈。
- 展开后能查看保留的原始输出；上游截断输出时也要保留截断提示与完整日志位置（如有）。
- 错误解释以证据为依据，建议与已执行动作分开。
- 检测到敏感信息时避免在摘要中再次复制；原始日志的存储、展示与导出脱敏需单独设计，不保证日志天然安全。
