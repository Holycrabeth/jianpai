# 产品需求

## 问题

Pi 的能力与可扩展性很有吸引力，但开发过程中直接出现的终端命令、英文状态和技术日志，对非专业开发者不友好。用户即使得到可用代码，也可能不理解过程中发生了什么。

## 产品定位

简派 = Pi 的开发能力 + 中文体验 + 面向非专业用户的过程解释。

不是削弱能力，也不是要求用户先学会编程术语。

## 分层目标

### 1. 界面中文化

逐步覆盖启动提示、帮助、设置、会话管理、模型选择、状态与错误。命令标识、模型名称、文件路径、API 字段等需要准确匹配的内容保留原样，配中文解释。

### 2. 工具呈现中文化（属于第一阶段整体汉化）

第一阶段只改显示文字，保持原有功能与操作。不以工具原型替代完整界面汉化。

常用工具统一用词：

| 工具 | 用户看到的说明 | 需要注意 |
| --- | --- | --- |
| `read` | 读取 | 不把读取成功说成理解正确 |
| `write` | 撰写 | 可能新建，也可能覆盖旧内容 |
| `edit` | 修改 | 保留修改前后差异 |
| `bash` | 执行终端命令 | 影响取决于命令，不能笼统称为安全 |

工具状态至少区分：进行中、完成、失败、取消。完成只代表该操作完成，不代表整个项目可用。

### 3. 非专业用户友好

- 重要操作前解释目的和可能影响，不为每一次琐碎读取刷屏。
- 出错时回答：哪里失败、已知原因、是否需要用户处理、下一步是什么。
- 使用两层信息：简洁中文说明 + 可查看的原始技术细节。
- 无法判断时直说，不编造命令用途或报错原因。

## 第一阶段范围

- 在原有终端内体验，不先做网页或桌面应用。
- 汉化启动、菜单、设置、模型、登录、会话、帮助与工具调用。
- 不先做解释卡片，遇到实际使用中的理解困难再逐步改善。
- 验证常用工具的中文调用标题及原有结果状态。
- 原始工具输入输出仍可查看，传给模型的数据不因中文展示而被篡改。
- 验证成功、失败、取消、长日志、中文路径等情况。
- 明确标注尚未汉化的 Pi 内置区域。

风险确认和额外过程解释均属于后续讨论，不是当前阶段的实现要求。首版不宣称提供安全沙箱或完备拦截。

## 暂不做

- 重写模型调用、工具执行和会话存储。
- 自动翻译代码、文件名、原始命令或所有日志行。
- 每次工具操作额外调用模型生成解释，增加费用与等待。
- 将简单关键词过滤包装成可靠安全机制。

## 验收标准

1. 用户能用自己的话说明刚才执行了什么操作。
2. 用户能分辨“操作成功”和“项目已经验证可用”。
3. 工具失败不能显示成成功；未知原因不能显示成确定诊断。
4. 用户可以找到对应的原始命令、输出和代码差异。
5. 中文呈现不改变工具行为、模型接收到的结果或原有错误语义。
6. 至少邀请一位非专业开发者试用，记录看不懂的地方。

## 后续需要和发起人确认

- 第一批使用者主要使用 macOS、Windows 还是其他系统？
- 是否接受先保留终端，之后再考虑独立图形界面？
- 更喜欢简洁进度，还是带少量知识解释的教学模式？
- 项目是否开源以及使用什么许可证？在确认前不作发布决定。
