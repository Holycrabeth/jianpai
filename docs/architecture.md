# 技术方案

## 决策 002：第一步以整体终端汉化为目标

发起人明确要求：先保留 Pi 原有功能，将界面文字直接翻成中文；后续在开发中遇到不好理解的地方再改善。不先开发解释卡片、教学模式或风险确认流程。

替代初始化阶段“工具扩展原型优先”的暂定方案。扩展不是必须坚持的实现手段。

## 当前实现：固定版本 + 可核对的显示补丁

采用 Pi `0.85.0` 的 npm 发布包，不修改全局 Pi，也不拷贝整个上游源码仓库：

1. `npm ci --ignore-scripts` 按锁文件安装依赖。
2. `scripts/build.mjs` 核对 Pi 版本和待修改文件的 SHA-256 指纹。
3. 将发布包复制到 `build/pi/`。
4. 在指定文件内替换代码中的文字常量与模板文字片段。
5. 应用少量显示适配：中文设置值、思考强度、模型列表字符宽度、中文工具标题。
6. 从生成副本的非打包 CLI 入口启动，使用独立用户配置。

原生工具已将执行模块与 `core/tools/renderers/` 分开；因此可以直接汉化渲染器，不需要重新注册或覆盖同名工具。

## 为什么不替换终端输出流

不能对 stdout 全文执行 `write → 撰写`：它会误改命令、日志、代码、文件名甚至协议。

简派使用 Acorn（JavaScript 语法解析器）定位字符串和模板片段，只翻译有明确文件范围的界面文案。模板表达式保持原样。词条匹配和代码语法都会验证。

菜单的显示值和实际值也分开。例如界面显示“开启”，保存和回调仍使用 `true`；显示“深入”，模型配置仍使用 `high`。第三方设置不会被强行套用这些翻译。

## 依赖用途

- `@earendil-works/pi-coding-agent@0.85.0`：原有 Pi 功能、工具、界面和配套文档。
- `@earendil-works/pi-server@0.85.0`：原生非打包入口引用的服务端模块。官方打包入口已内嵌此模块，但其非打包入口未声明该依赖，因此显式补齐，避免启动时模块缺失；不主动启动服务。
- `acorn@8.15.0`：仅用于开发构建阶段解析代码，不在运行时翻译输出。

所有直接依赖固定版本，完整依赖树由 `package-lock.json` 固定。

## 配置与兼容性

启动器保留调用者的工作目录、参数及终端流。用户配置默认隔离在 `~/.jianpai/agent/`，项目资源目录仍为 `.pi/`。

通过生成副本的 `piConfig.name` 使用 `jianpai` 身份；不修改原包名、模型 API、工具参数或会话格式。官方分发版专属的首次引导可能因品牌识别而不触发，用户可直接使用中文 `/login` 和 `/settings`。

默认关闭上游启动版本检查和安装统计；这不等于禁止模型或工具联网。简派版本更新应通过审核依赖、重新构建完成，不通过 Pi 的全局自更新分发汉化版本。

## 验证与维护

- `npm run check` 验证上游指纹、语法、生成文件同步，并核对工具执行、系统提示词、会话存储与凭据模块和原包逐字节一致。
- `npm test` 覆盖中文显示、设置回调、窄终端、真实工具操作、失败、取消、日志保留与独立入口。
- `npm run demo` 使用临时目录实际运行四个工具，结束后清理。
- 终端实际交互通过独立 tmux 会话手动验证，不复用用户当前会话。
- 尚未进行真实服务商登录及付费模型端到端验证，不将本地工具测试说成线上验证。

升级时先读对应版本文档及代码、更新词条和测试，再显式执行 `node scripts/build.mjs --record-upstream` 更新指纹。不得只刷新指纹来绕过不兼容。
